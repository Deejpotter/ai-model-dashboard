Usage & Subscription Cost — Deep-Dive Report

Investigation of why the $60 included-allowance display is not useful, with real evidence from the codebase, schema, and live UI.

Project: ai-model-dashboard Scope: Cost planner / subscription usage display Evidence date: 19 Oct 2026 Status: P0 — Decision quality

1. What I was asked — reasoning first

When you said “This isn't a very useful data. I would like the usage to show what the usage would be because the token usage still comes out of the $60,” the complaint was about the subscription-model billing text shown in the card/detail view (your screenshot: From $10.00 / month — includes $60 of model usage each month).

My interpretation (verified against code) For subscription routes (e.g. GitHub Copilot-style $10/mo with $60 included usage), the interface shows the allowance as static text but never computes how much of it has been consumed by the current workload scenario. The planner calculates pure token cost (calculateCost) ignoring both subscription_monthly and included_usage_usd. The result: a user planning an agent workload cannot tell whether their usage fits inside the $60 allowance (effective cost = just $10 fee) or exceeds it (fee + overage).

2. Investigation — evidence from the app

2.1 The screenshot matches the static billing() output

Your image matches exactly the subscription branch of billing() at Dashboard.tsx:24:

const billing = (m: Model, monthly: number | null) => isFreeModel(m) ? { label: 'Free', detail: ... } : m.subscription_monthly != null ? { label: `From ${money(m.subscription_monthly)} / month`, detail: m.pricing_note ?? (m.included_usage_usd != null ? `Includes ${money(m.included_usage_usd)} of model usage` : 'Subscription route'), state: 'subscription' } : ...

Note: the detail is hard-coded to the allowance amount ($60), never to actual consumption. There is no parameter for “used so far” and no calculation of remaining balance.

2.2 The planner ignores subscription economics entirely

calculateCost (line 22) is pure token arithmetic:

const calculateCost = (m: Model, input, output, cache) => m.price_input == null || m.price_output == null || (cache > 0 && m.price_cache_read == null) ? null : input * (1 - cache/100) / M * m.price_input + input * cache/100 / M * (m.price_cache_read ?? 0) + output / M * m.price_output; // <— no subscription check

Consequence: a $10/mo subscription model with $60 included usage will show, say, $12.40 for a heavy scenario — implying you pay $12.40 on top of $10, when in reality you might still be inside the $60 bucket.

2.4 Seed data confirms the gap

All 25 seeded models (seed-data.ts) have price_input and price_output populated, but none populate subscription_monthly or included_usage_usd — the fields are present in the DB schema but not exercised in data. This means the subscription display is essentially untested in production scenarios.

P0 finding — decision quality
The planner can rank a subscription model lower (or higher) than it should be because it compares raw token cost against a metered route, ignoring that the first $60 is prepaid. Users making a shortlist are comparing incomparable cost structures.

2.5 No feedback loop: usage never feeds back into the card

The model card (ModelCard, line 54) renders price.label and price.detail once. There is no state for used_usd, remaining_usd, or scenario_cost_vs_allowance. The comparison tray and detail drawer also only show monthly (the planner's raw cost), never the effective subscription cost.

4. Recommendations

R1 — Compute usage in dollar terms (P0)

Add a scenario-cost vs allowance calculation path:

  • If model has subscription_monthly and included_usage_usd, compute raw_cost = calculateCost(...).
  • If raw_cost <= included_usage_usd, effective cost = subscription_monthly (only fee; usage is covered).
  • If raw_cost > included_usage_usd, effective cost = subscription_monthly + (raw_cost - included_usage_usd).
  • Display both numbers: Usage cost: $X (of $60 included) and Effective monthly: $Y (fee + overage).

R2 — Change billing text from static to computed (P0)

Replace Includes ${money(included_usage_usd)} of model usage with a computed string based on current planner scenario, e.g. Usage: $12 / $60 included · Effective: $10/mo or $78 / $60 · Over by $18.

R3 — Separate “Subscription” and “Metered” comparison logic (P0)

In comparison view and planner, tag rows by pricing mode (subscription / metered / free) so users never compare a $10-fee plan against a $0-fee-but-pay-per-token route without the context of the allowance.

R4 — Add usage/consumption fields or scenario-state (P1)

Introduce either a session-state object (scenarioUsedUsd, scenarioRemainingUsd) or a lightweight DB table if persistent tracking is needed. At minimum, the planner should expose budget comparison against both raw and effective cost.

R5 — Surface source/freshness for subscription claims (P1)

When showing "Includes $60 of model usage," also show last_updated / pricing_note source so users know the allowance figure is from the provider and when it was verified.

5. How this connects to the broader audit

The existing docs/ux-audit-and-redesign-proposal.md (prepared 18 Oct 2026) already flags P0 cost-calculation errors (null prices treated as zero) and P0 too-much-information-at-once (12-column table). The subscription-usage gap is a new P0 that intersects both: even with perfect pricing data, the planner misrepresents subscription economics because the allowance is never subtracted from the token cost.

Recommended next step
Before redesigning the catalogue layout (Phase 1 of the audit proposal), fix R1 + R2. They are code-only changes to Dashboard.tsx (update calculateCost, billing, and the planner projection list) and do not require DB schema changes for an initial version, since the planner already holds input, output, cache state.
